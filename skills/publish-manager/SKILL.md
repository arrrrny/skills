# Publish Manager

Orchestrates the full release and publication workflow for a project.

When activated, the agent should follow the workflow below. On first run for a project, it discovers project-specific scripts and conventions and saves them to a `PUBLISH.md` at the project root. On subsequent runs, it reads from that file to skip re-discovery.

## When to Use

Use this skill when the user says something like:

- "Publish version 1.2.3"
- "Release a new version"
- "Prep and publish the packages"
- "Run the release flow"
- Any request involving cutting a release, publishing packages, or deploying

## Workflow

### 1. Determine Version

- If the user provides a version number (e.g., "publish 4.5.0"), use it directly.
- If no version is given, read the current version from the root `pubspec.yaml` (or `package.json`, etc.) and suggest a bump based on the scope of changes:
  - Breaking changes → bump major
  - New features → bump minor
  - Bug fixes only → bump patch
  - Ask the user to confirm before proceeding.

Validate the version is a valid semver (`X.Y.Z`).

### 2. Check for Project Publish Configuration

Look for `PUBLISH.md` at the project root (the outermost root directory of the current project). If it exists, read it — it contains project-specific scripts and conventions discovered on a previous run.

If `PUBLISH.md` does **not** exist (first run for this project), perform discovery (see Step 6 below), then proceed.

### 3. Update Changelogs

Use the **changelog-manager** skill to update all `CHANGELOG.md` files. Activate that skill and follow its instructions:

1. Generate or obtain changelog content based on uncommitted changes / git log since last tag.
2. Prepend the new version entry to every `CHANGELOG.md` in the project.
3. Verify the updates.

### 4. Validate Version Constraints

Before running pre-publish scripts, validate that **no package** has `any` as a version constraint. Pub.dev rejects packages that declare `dependency: any` in their `pubspec.yaml`.

1. Search all `pubspec.yaml` files for the pattern `: any` (excluding commented lines):
   ```
   grep -rn ": any" --include="pubspec.yaml" . | grep -v "^.*#.*: any"
   ```
2. For each match found:
   - If it's in a published package (listed in PUBLISH.md), **block the workflow** — the user must fix it first.
   - If it's in a non-published package (e.g., example, dev tools), replace with a realistic caret constraint (e.g., `^X.Y.Z` where X.Y.Z is the currently resolved version from `pubspec.lock`).
3. Re-run the check until zero matches remain before proceeding.

### 5. Run Pre-Publish Scripts

If a pre-publish script is defined in `PUBLISH.md` (e.g., `./scripts/prepare_for_publish.sh <version>`), run it. This script typically:

- Creates a release branch (e.g., `publish-<version>`)
- Updates version numbers across all packages
- Converts path dependencies to versioned references
- May also update changelogs (but the changelog-manager skill already did this)

Pre-publish scripts often take the version number as an argument. Pass it.

If no pre-publish script is configured, still create a release branch manually:

```
git checkout -b publish-<version>
```

### 6. Commit and Push

Commit all changes with a message like `"Prepare for publishing version <version>"` (or read the configured commit pattern from `PUBLISH.md`).

Push the branch to origin:

```
git push origin publish-<version>
```

### 7. Run Publish Script

Find and run the publish/release script. Check (in order of priority):

- The script path configured in `PUBLISH.md`
- `./scripts/publish.sh`
- `./scripts/release.sh`
- `./publish.sh`
- `./release.sh`
- `make publish`
- Other common patterns

Publish scripts may be interactive (asking for confirmation before publishing to pub.dev, npm, etc.). Run them as-is.

After publishing completes successfully, create and push a git tag for the version if the publish script doesn't already do so:

```
git tag <version>
git push origin <version>
```

### 8. First-Run Discovery (Create PUBLISH.md)

If `PUBLISH.md` does not exist at the project root, create it after the first successful run. Discover the following:

```markdown
# Publish Configuration for `<project-name>`

<!-- Auto-generated by publish-manager skill on <date>. Edit if the workflow changes. -->

## Package Manager

- **Type**: `pub.dev` (or `npm`, `cargo`, etc.)
- **Packages**: List packages and publish order
- **Public packages**: Which packages are published to a public registry
- **Private packages**: Which packages are internal only

## Scripts

- **Pre-publish**: `./scripts/prepare_for_publish.sh <version>` — creates branch, updates versions
- **Publish**: `./scripts/publish.sh` — publishes all packages in dependency order
- **Post-publish**: `./scripts/push_to_master.sh` — merges publish branch to master
- **Restore dev**: `./scripts/restore_dev_setup.sh` — reverts to path dependencies

## Workflow

1. Update changelogs
2. `./scripts/prepare_for_publish.sh <version>`
3. Commit and push
4. `./scripts/publish.sh`
5. `./scripts/push_to_master.sh`
6. `./scripts/restore_dev_setup.sh`

## Notes

- Any additional context learned during the first run
```

### 9. Post-Publish Steps

After publishing, ask the user if they want to:

- Merge the publish branch into main/master and push (if a script exists like `push_to_master.sh`, offer to run it)
- Revert to development setup (if a script exists like `restore_dev_setup.sh`, offer to run it)
- Delete the publish branch locally

## Design Notes

- The skill is global so it works across all projects.
- On first run per project, it discovers and persists project-specific details in `PUBLISH.md`.
- On subsequent runs, it reads from `PUBLISH.md` to go straight to the workflow without re-discovery.
- If the user updates their workflow, they can edit `PUBLISH.md` manually and the skill will use the updated configuration.
- The skill delegates changelog management to the `changelog-manager` skill if available.
- Run scripts as-is — the skill does not modify them.
- **Google Play release notes limit**: Each locale's "What's New" notes are capped at **500 characters** by the Play Store API. If Fastlane fails with `release created has notes in language ... with length N, which is too long (max: 500)`, shorten the offending locale's release notes in `RELEASE.md` below the limit and re-run the publish step.
